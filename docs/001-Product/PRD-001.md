## Purpose

This document defines the complete product requirements for Ferret version 1.0. It is the authoritative reference for what the product is required to do. It does not describe how requirements will be implemented — implementation decisions belong in Architecture documents and ADRs.

This document is intended to be read by architects, engineers, AI agents operating within the platform, contributors, plugin developers, and enterprise customers. It must be sufficient on its own to give any reader a complete and unambiguous understanding of the product's expected behaviour.

## 1. Executive Summary

Ferret is an open-source platform that gives AI systems structured, persistent, repository-local knowledge of the software projects they are used to support. The platform mediates every AI interaction with a codebase through a governed engineering workflow: specifications are written before code, decisions are recorded as ADRs, all AI-generated artefacts are subject to human review, and every interaction is traceable.

The product addresses a set of structural limitations in current AI-assisted development tooling that cannot be resolved through model capability improvements alone. These limitations — described in Section 3 — arise from the absence of platform-layer infrastructure, not from insufficient model intelligence.

Ferret is positioned as **the AI Workspace Operating System**: the foundation layer on which AI-assisted engineering workflows are built, regardless of the models, tools, or services those workflows consume.

This document defines the requirements for Ferret 1.0. For the long-term vision, see VISION-001. For the project mission, success criteria, and sustainability model, see MISSION-001. For the engineering principles that govern all design decisions, see PRINCIPLES-001. For canonical term definitions used throughout this document, see GLOSSARY-001.

## 2. Product Overview

### 2.1 Product Identity

Ferret is **the AI Workspace Operating System** — a platform that structures, governs, and persists AI-assisted engineering activity within a software repository.

The product is defined by seven characteristics:

**AI Agnostic.** Ferret does not couple its behaviour to any specific AI model or provider. Model selection is a configuration concern. Changing the model requires no change to the platform or to its accumulated knowledge. This principle is stated as a constraint in PRINCIPLES-001, Principle 1.

**Repository First.** The repository is the canonical source of all knowledge the platform holds. Every piece of information the platform acts on — source symbols, specifications, decisions, interaction history — is derived from or stored within the repository. Nothing important exists only outside version control.

**Specification Driven.** The platform enforces the discipline that software is specified before it is implemented. It provides first-class tooling for authoring, reviewing, and linking specifications to implementations. This principle is stated as a constraint in PRINCIPLES-001, Principle 2.

**Plugin First.** The core platform is minimal and stable. Every domain-specific capability — model providers, storage backends, language parsers, review workflows — is delivered through the plugin system. This principle is stated as a constraint in PRINCIPLES-001, Principle 3.

**Enterprise Ready.** The platform is designed from the outset to operate in regulated, access-controlled environments. Its state is auditable, its AI interactions are logged, its configuration is version-controlled, and it supports on-premise, air-gapped deployment.

**Open Source.** The core platform is released under the MIT licence. The plugin interfaces are open and stable. No capability required for basic operation is proprietary. The governance model and decision history are public.

**Local First.** The platform operates without any external hosted service. A team running the platform with local model inference, local storage, and local plugin installation has access to the complete feature set with no data leaving their network boundary.

### 2.2 What Ferret Is Not

Ferret is not an IDE, a source control system, an issue tracker, a build server, or an AI model. It does not replace any of these systems. It integrates with them through its plugin and MCP interfaces. Explicit non-goals are listed in Section 9.

## 3. Problem Statement

The following problems are structural limitations of the current generation of AI-assisted development tooling. They are not fully addressable through model capability improvements because they arise from the absence of platform-layer infrastructure.

**P-001 — AI Context Loss.** AI models have no persistent memory of past interactions with a repository. Every session begins without knowledge of the project's architecture, its past decisions, or its conventions. Engineers re-establish this context repeatedly, investing time in work that produces no durable result.

**P-002 — Repository Fragmentation.** A project's knowledge is distributed across version control, issue trackers, design documents, chat logs, and team memory. No single system presents a coherent, queryable view. AI tools connected only to source code operate with an incomplete and structurally misleading picture of the project.

**P-003 — Lack of Engineering Traceability.** In AI-assisted workflows, there is no standard mechanism to link a generated artefact — a code block, a specification, a review finding — to the input that produced it, the model that produced it, or the human who reviewed it. This makes auditing, debugging, and accountability structurally absent.

**P-004 — Poor Knowledge Reuse.** Architectural decisions, coding conventions, and design rationale are re-derived repeatedly across sessions because they are not stored in a form accessible to AI systems. The investment in producing this knowledge is made once; the benefit is not compounded.

**P-005 — Vendor Lock-in.** Engineering teams that invest deeply in a proprietary AI toolchain couple their workflows to that vendor's pricing, capability decisions, API changes, and deprecation schedule. This creates a dependency with no contractual mitigation for most teams.

**P-006 — Large Repository Limitations.** Current AI tools degrade significantly on repositories above a certain size because they cannot selectively load relevant context. A full-context approach is not practical on large codebases; a structured, queryable knowledge layer is required.

**P-007 — AI Memory Limitations.** Context windows are finite. Without a mechanism to selectively load relevant knowledge into context, engineers must manually curate what the AI sees. This is cognitively expensive and produces inconsistent results.

**P-008 — Repeated Prompt Engineering.** Teams invest significant effort in writing and maintaining prompts that establish project context. This work is fragile, undocumented, and not version-controlled. When the model changes, the prompts require renegotiation.

**P-009 — Missing Engineering Governance.** AI tools generate code and content at speed. Without a governance layer — specifications, reviews, approvals — this speed produces artefacts that are not traceable, not tested, and not aligned with stated requirements.

**P-010 — Knowledge Silos.** Individual engineers accumulate project understanding that is not available to their teammates or to AI systems. When an engineer leaves the team, their knowledge is lost. There is no standard mechanism to make implicit knowledge explicit and persistent.

## 4. Existing Market Analysis

This section analyses the categories of tooling that address adjacent problems. The purpose is to identify where Ferret fits relative to existing categories, not to compare specific products.

### 4.1 AI Coding Assistants

AI coding assistants integrate into editors and provide inline code completion, generation, and explanation. They operate at the file or function level. They have limited or no awareness of project-level architecture, specifications, or decision history. Their context is typically scoped to the open files and a configurable window of recent code. They do not provide a governance layer, do not maintain persistent project knowledge, and do not support AI-model-agnostic deployment.

**Where Ferret fits:** Ferret is not an AI coding assistant. It provides the knowledge layer and governance infrastructure that makes coding assistants more effective by giving them structured context about the project. It integrates with assistants through its MCP server rather than replacing them.

### 4.2 IDE Assistants

IDE-integrated AI assistants extend AI coding assistants with deeper editor integration: refactoring, navigation, test generation, and documentation. Their knowledge of the project is derived from the IDE's language server and the open workspace. They operate within the IDE's session and do not persist knowledge across sessions or make it available to other tools.

**Where Ferret fits:** Ferret is not an IDE assistant and does not require an IDE to operate. It provides session-independent, persistent knowledge accessible to any MCP-compatible host, including IDE-integrated assistants.

### 4.3 Agent Platforms

Agent platforms provide infrastructure for executing multi-step AI reasoning tasks. They define agent architectures (reasoning loops, tool use, memory), provide runtime orchestration, and may support multi-agent coordination. They do not typically enforce engineering discipline (specification-first, human review), do not provide repository-local knowledge, and are generally not repository-native.

**Where Ferret fits:** Ferret provides an agent runtime scoped specifically to engineering workflows. It is not a general-purpose agent platform. Its agent runtime is governed by the specification-driven, human-review constraints described in PRINCIPLES-001.

### 4.4 Knowledge Platforms

Enterprise knowledge platforms provide searchable repositories of documents, policies, and decisions. They are not designed for software engineering workflows specifically and do not integrate with version control, source parsing, or AI model interfaces. They treat documents as static assets rather than as live artefacts linked to evolving codebases.

**Where Ferret fits:** Ferret provides a knowledge layer specific to software repositories. Knowledge is derived from source code, specifications, ADRs, and AI interactions — not from general organisational documents. The knowledge index is version-controlled alongside the code it describes.

### 4.5 Documentation Systems

Documentation generation tools extract documentation from source code and produce static sites or wiki-style outputs. They operate on the current state of the codebase and do not maintain knowledge about requirements, decisions, or the evolution of the codebase over time.

**Where Ferret fits:** Ferret is not a documentation generator. It consumes documentation (specifications, ADRs, architecture documents) as inputs to its knowledge layer and provides tooling for authoring and reviewing them, but it does not produce static documentation outputs.

### 4.6 Search and Code Intelligence Systems

Code search and intelligence systems provide symbol navigation, reference lookup, and cross-repository search. They index source code for developer navigation. They do not model the relationship between code and the requirements, specifications, and decisions that drove it.

**Where Ferret fits:** Ferret provides a search capability over its knowledge index that includes source symbols, but its primary purpose is to make that knowledge available to AI systems as structured context, not to provide developer navigation interfaces.

### 4.7 Ferret's Unique Position

Ferret occupies the platform layer between repositories and AI models. No current category provides: persistent, repository-local knowledge; AI-model-agnostic interfaces; specification-driven workflow enforcement; human review governance; and a plugin architecture for capability extension — in a single, open-source, locally deployable platform.

## 5. Target Users

The platform is designed for the following user populations. Detailed personas follow in Section 6.

| User Type | Description |
|---|---|
| **Individual Developer** | An engineer working on a personal or small-team project who uses the platform to maintain persistent AI context and enforce engineering discipline |
| **Open Source Maintainer** | An engineer managing a community project who uses the platform to onboard contributors, document architecture decisions, and maintain specification coverage |
| **Engineering Team** | A team of engineers working on a shared codebase who use the platform to share knowledge, enforce standards, and coordinate AI-assisted workflows |
| **Enterprise Engineering** | A large engineering organisation with compliance and audit requirements who uses the platform as governed AI infrastructure for multiple teams |
| **Platform Team** | A team responsible for shared engineering infrastructure who deploys and operates Ferret as a service for other engineering teams |
| **Solution Architect** | An architect who uses the platform to author and review architecture documents, record decisions, and validate implementation against architectural intent |
| **Technical Lead** | A senior engineer who uses the platform to set and enforce team engineering standards and to track specification and review coverage |
| **AI Plugin Developer** | A developer who builds extensions to the platform — model providers, storage backends, tool integrations, workflow plugins |

## 6. User Personas

### Persona 1 — Alex: Individual Developer

**Background.** Alex is a mid-career software engineer working on a personal project that has grown to approximately 80,000 lines of code across 12 modules. Alex has been the sole contributor for three years. The codebase predates AI coding tools and was not designed with AI assistance in mind.

**Goals.**
- Use AI assistance that understands the project's history and conventions without repeated context-setting
- Maintain architecture discipline as the codebase grows
- Produce traceable, reviewable decisions even when working alone

**Pain Points.**
- Every AI session starts with ten minutes of context re-establishment
- Architectural decisions made years ago are not documented; rationale is lost
- AI suggestions frequently contradict established patterns in the codebase

**Typical Workflow.** Alex opens a session, begins implementing a feature, finds that the AI does not know about a relevant pattern established three modules earlier, and spends time re-explaining it. The same explanation was given in the previous session.

**Ferret Benefits.** Ferret indexes Alex's repository once. Subsequent sessions automatically load relevant context. Architectural decisions are recorded as ADRs and become part of the knowledge the AI draws on. Suggestions that contradict established patterns can be flagged against the knowledge index.

### Persona 2 — Marisol: Open Source Maintainer

**Background.** Marisol maintains a moderately popular open-source library with fifteen regular contributors and several hundred users. The repository has been active for four years and has accumulated significant undocumented architectural complexity.

**Goals.**
- Onboard new contributors faster by making project knowledge accessible
- Document architectural decisions that currently exist only in issue comments and chat
- Maintain consistent standards across contributions from many different authors

**Pain Points.**
- New contributors repeatedly ask questions that are answered in pull request discussions from years ago
- There is no consistent specification process; features are sometimes implemented before the requirement is clear
- Code review findings are not tracked; the same issues recur

**Typical Workflow.** Marisol reviews a pull request, identifies a violation of an undocumented convention, leaves a comment explaining it, merges the PR, and sees the same violation in the next contribution from a different author.

**Ferret Benefits.** Conventions are codified in the knowledge index and in specifications. New contributors can query the project's standards before submitting. Recurring review findings are tracked and can be referenced in automated review workflows.

### Persona 3 — Dmitri: Engineering Team Lead

**Background.** Dmitri leads a team of eight engineers on a product that has been in development for three years. The team uses a modern stack and has a reasonable test suite, but specification discipline is inconsistent. Engineers sometimes implement features before requirements are clear, leading to rework.

**Goals.**
- Enforce a specification-first process without adding bureaucratic overhead
- Give the team AI assistance that is grounded in the project's actual requirements and architecture
- Produce reviewable, approvable AI contributions that meet the team's quality standard

**Pain Points.**
- Specifications are written in a wiki that is not linked to implementation; they drift from the actual code
- AI-generated code is reviewed for correctness but not for compliance with stated requirements, because the tools do not know about the requirements
- Architectural decisions are made in Slack and are not recorded anywhere durable

**Typical Workflow.** Dmitri asks an engineer to implement a feature. The engineer writes the code, creates a PR, and it is reviewed for code quality. Whether the implementation actually satisfies the requirement is not assessed systematically, because the reviewer does not have the requirement in front of them.

**Ferret Benefits.** Specifications are authored and approved through the platform. AI-assisted code review validates implementation against the specification's acceptance criteria. ADRs give the team a durable record of architectural discussions.

### Persona 4 — Ingrid: Enterprise Platform Engineer

**Background.** Ingrid is part of a platform engineering team responsible for shared developer infrastructure at a large engineering organisation. The organisation has compliance requirements that mandate audit trails for all AI-generated artefacts. The organisation operates on-premise and cannot send source code to external services.

**Goals.**
- Deploy AI-assisted engineering tooling that satisfies audit and compliance requirements
- Provide all engineering teams with a consistent, governed AI interface to their repositories
- Operate entirely within the organisation's network boundary

**Pain Points.**
- Every AI tool evaluated requires sending code to an external API, which is prohibited by policy
- AI tools do not provide audit logs adequate for compliance review
- There is no consistent way to configure AI tooling across many different teams and repositories

**Ferret Benefits.** Ferret deploys on-premise with locally operated model inference. All AI interactions are logged with model identifier, user identity, and timestamp. The platform's configuration is version-controlled and applies consistently across repositories.

### Persona 5 — Farid: Plugin Developer

**Background.** Farid is an independent software engineer who has identified that there is no Ferret plugin for their team's internal issue-tracking system. Farid wants to build and publish a plugin that integrates Ferret's review workflow with the issue tracker.

**Goals.**
- Build a plugin using the plugin SDK without needing to understand the platform's internals
- Publish the plugin so other teams using the same issue tracker can benefit from it
- Maintain the plugin without coupling it to internal platform releases

**Pain Points.**
- Current AI tools that could be extended either have no extension mechanism or require modifying the tool's source code
- Plugins for existing tools do not have stable, versioned interfaces; upgrades break them

**Ferret Benefits.** The Plugin SDK provides a stable, versioned interface. The plugin manifest declares the permissions required. The plugin can be developed and tested against the plugin contracts without the full platform source.

### Persona 6 — Yuki: Solution Architect

**Background.** Yuki is a principal architect responsible for the architecture of a multi-team platform. Yuki needs to communicate architectural intent to many engineers, validate that implementations comply with architectural decisions, and maintain a record of decisions made over three years of development.

**Goals.**
- Make architectural decisions discoverable and queryable by all engineers
- Validate that proposed changes comply with recorded architectural decisions
- Produce architecture reviews that are formal, trackable, and resolved

**Pain Points.**
- ADRs written in the past are stored in a folder that engineers rarely consult
- Architecture violations in code are discovered only at review time, not when the code is written
- Architecture reviews are informal documents with no structured finding or resolution process

**Ferret Benefits.** ADRs are part of the knowledge index and can be referenced in AI context assembly. The review engine produces structured findings with resolution tracking. Architecture compliance can be assessed as part of the standard review workflow.

## 7. User Journeys

### Journey 1 — New Repository Onboarding

**Actor:** Individual Developer (Alex)  
**Precondition:** A repository exists with source code and no Ferret configuration.

1. The developer runs `Ferret init` in the repository root.
2. The platform detects the repository structure, creates the `.ai/` directory, and generates a default `workspace.json`.
3. The developer runs `Ferret index build`.
4. The platform indexes all source files, documents, and existing structured content (README, any existing ADRs or specs).
5. The platform reports index coverage: number of files processed, symbols extracted, documents indexed.
6. The developer runs `Ferret workspace status`.
7. The platform reports workspace health: index currency, knowledge coverage, any missing configuration.
8. The developer's AI assistant, configured with Ferret's MCP server, can now answer questions about the repository using the indexed knowledge.

**Success Condition:** The AI assistant answers a question about the repository that it could not answer before indexing, using knowledge from the index.

---

### Journey 2 — Existing Repository Integration

**Actor:** Engineering Team Lead (Dmitri)  
**Precondition:** An existing repository with two years of history, existing documentation, and some ADRs written manually.

1. The team lead runs `Ferret init` and configures the workspace to include the team's existing ADR folder and specification wiki export.
2. The platform indexes source code and existing documentation, recognising the ADR format used by the team.
3. The platform produces an index coverage report identifying files and document types that are not indexed.
4. The team lead reviews the coverage report and configures exclusions for generated files and third-party code.
5. The team runs `Ferret index build --full` to produce an authoritative first index.
6. Existing ADRs appear in knowledge queries. Engineers can ask the AI "what was the decision on the caching strategy" and receive an answer referencing ADR-0014.

**Success Condition:** Existing documentation is queryable through the platform without requiring reformatting or migration.

---

### Journey 3 — Daily Development

**Actor:** Individual Developer (Alex)  
**Precondition:** Ferret is initialised and indexed. A specification for the current feature has been approved.

1. The developer begins a session. The platform loads the current session context from `.ai/session.md`.
2. The developer runs `Ferret context load --spec SP-042` to prime the AI context with the specification.
3. The AI assistant receives the specification's acceptance criteria, related ADRs, and relevant source symbols as structured context.
4. During development, the developer asks the AI to review a function. The review references the specification's acceptance criteria.
5. The developer runs `Ferret index update` after completing a set of changes.
6. Changed files are re-indexed incrementally. The index reflects the new state.
7. At the end of the session, the developer runs `Ferret session save`.
8. The platform records the session's active work items, decisions made, and files modified to `.ai/session.md`.

**Success Condition:** The next session resumes with the context of the previous session loaded automatically.

---

### Journey 4 — Specification Authoring

**Actor:** Engineering Team Lead (Dmitri)  
**Precondition:** A feature request has been approved and a work item exists in the issue tracker.

1. The team lead runs `Ferret spec create --id SP-055 --title "Agent execution timeout handling"`.
2. The platform generates a specification draft using the template, pre-populated with the workspace's project metadata and linked to the work item identifier.
3. The AI assistant, using the knowledge index, suggests relevant ADRs and existing specifications that are related.
4. The team lead authors the acceptance criteria and scope sections.
5. The team lead submits the specification for review: `Ferret spec submit SP-055`.
6. The platform marks the specification as "In Review" and notifies configured reviewers.
7. A reviewer approves the specification: `Ferret spec approve SP-055`.
8. The platform marks the specification as "Approved" and makes it available for context loading in development sessions.

**Success Condition:** The specification is linked to the work item, approved, and available in the knowledge index. No implementation has begun.

---

### Journey 5 — Architecture Review

**Actor:** Solution Architect (Yuki)  
**Precondition:** A significant architectural change has been proposed and an ADR draft exists.

1. The architect runs `Ferret review create --type AR --scope "proposed-storage-backend"`.
2. The platform generates a review document from the architecture review template, linked to the proposed ADR.
3. The AI assistant analyses the proposed ADR against existing ADRs and the architecture overview, generating an initial set of findings for the architect to evaluate.
4. The architect reviews each AI-generated finding, accepting or rejecting it, and adds manual findings.
5. Each finding is categorised by severity: Critical, High, Medium, Low, or Observation.
6. The architect submits the review: `Ferret review submit AR-005`.
7. The proposer addresses each finding and marks it resolved with a note.
8. The architect confirms resolution and approves the review: `Ferret review approve AR-005`.
9. The ADR's status is updated to Accepted.

**Success Condition:** The review is fully resolved, the ADR is accepted, and both documents are in the knowledge index.

---

### Journey 6 — Code Review

**Actor:** Engineering Team Member  
**Precondition:** A pull request has been opened for a feature with an approved specification.

1. The engineer runs `Ferret review generate --diff HEAD~1 --spec SP-055`.
2. The platform assembles context from the diff, the linked specification, and the knowledge index.
3. The AI produces a structured review covering: specification compliance, principle adherence (per PRINCIPLES-001), and code quality observations.
4. The review is presented to the engineer as a list of findings with severity, location, and description.
5. The engineer reviews each finding, marking each as accepted, rejected, or deferred.
6. The engineer commits the approved review record alongside the pull request.
7. The human reviewer can see both the AI findings and the engineer's dispositions before completing their review.

**Success Condition:** The merged pull request contains a traceable record of AI-assisted review findings and their dispositions.

---

### Journey 7 — Plugin Development

**Actor:** Plugin Developer (Farid)  
**Precondition:** Ferret is installed. The plugin SDK is available.

1. Farid runs `Ferret plugin scaffold --id "Ferret.acme.issue-tracker" --type "review-publisher"`.
2. The platform generates a plugin project scaffold: manifest, entry point, and SDK reference.
3. Farid implements the `IReviewPublisher` interface, referencing the SDK documentation.
4. Farid runs `Ferret plugin validate` to check the manifest and implementation against the plugin contract.
5. Farid runs `Ferret plugin install --local ./Ferret.acme.issue-tracker` to install the plugin in a test workspace.
6. Farid runs the review workflow and verifies that findings are published to the issue tracker.
7. Farid packages the plugin: `Ferret plugin pack`.
8. Farid publishes the plugin to the registry.

**Success Condition:** The plugin is installed, functional, and published without Farid having read the platform's core source code.

---

### Journey 8 — CI/CD Integration

**Actor:** Platform Team (Ingrid's team)  
**Precondition:** Ferret is installed and indexed. A CI/CD pipeline exists.

1. The platform team adds an `Ferret index update` step to the CI pipeline that runs on every merge to the main branch.
2. The step runs incrementally, updating only the files changed in the merge commit.
3. The pipeline also runs `Ferret review generate --diff HEAD~1 --spec auto` as a required check.
4. The review check passes if there are no Critical or High findings unaddressed.
5. On a weekly schedule, the pipeline runs `Ferret workspace health --report` and publishes the report as a pipeline artefact.
6. The health report includes: index coverage, specification coverage, ADR count by status, open review findings.

**Success Condition:** The CI pipeline enforces specification coverage and review quality gates automatically.

---

### Journey 9 — Large Repository Maintenance

**Actor:** Engineering Team Lead (Dmitri)  
**Precondition:** A repository with 200,000 source files and a growing knowledge index.

1. The team lead runs `Ferret index health`.
2. The platform reports: total indexed files, last update time, files changed since last update, index size, and any inconsistencies detected.
3. The team lead runs `Ferret index update` to synchronise with recent changes.
4. The platform processes only the files changed since the last index run. Files not in the changeset are not re-processed.
5. The team lead queries: `Ferret knowledge query "modules that depend on the authentication interface"`.
6. The platform returns the set of modules that reference `IAuthenticationProvider`, derived from the index, in under two seconds.
7. The team lead runs `Ferret index compact` to perform periodic maintenance: removing stale entries for deleted files and consolidating index segments.

**Success Condition:** Index operations scale with changeset size, not repository size. The full repository is navigable through the knowledge index.

## 8. Goals

### 8.1 Product Goals

**PG-001.** Enable AI assistants to answer repository-specific questions that require understanding of architecture, decisions, and specifications — not just source code.

**PG-002.** Provide a specification workflow that is lightweight enough for individual developers and rigorous enough for enterprise teams.

**PG-003.** Make repository knowledge portable: indexable, version-controlled, and reproducible from source files without external dependencies.

**PG-004.** Provide a review workflow that makes human oversight of AI-generated artefacts tractable and traceable.

**PG-005.** Operate with full feature parity on Linux, macOS, and Windows.

### 8.2 Engineering Goals

**EG-001.** All platform behaviour must be predictable, deterministic, and testable without live AI model access or external infrastructure.

**EG-002.** The plugin interface must be sufficiently stable that a plugin written for version 1.0 requires no code change to work with any 1.x release.

**EG-003.** Incremental index operations must complete in time proportional to the changeset, not the repository size.

**EG-004.** All AI interactions must be traceable from committed artefact to model invocation, including the knowledge state at the time of the interaction.

**EG-005.** The platform must be deployable without any external network connectivity.

### 8.3 Community Goals

**CG-001.** The contribution process must allow a new contributor to make a meaningful first contribution within a single working session.

**CG-002.** The plugin SDK must be documented sufficiently that a plugin developer can build, test, and publish a plugin without reading the platform's core source code.

**CG-003.** The governance model must allow the project to continue operating if any individual maintainer becomes unavailable.

### 8.4 Enterprise Goals

**EntG-001.** All AI-generated artefacts committed to a repository must carry traceable metadata (model, user, timestamp, knowledge state hash) that satisfies audit requirements.

**EntG-002.** Sensitive repository content (secrets, credentials, private keys) must be excluded from the knowledge index by default with explicit opt-in required to include any file matching configurable patterns.

**EntG-003.** Access to AI capabilities must be configurable per-user and per-repository through a documented permission model.

**EntG-004.** The platform must produce machine-readable health and compliance reports suitable for integration with enterprise monitoring systems.

---

## 9. Non-Goals

The following are explicit boundaries. Ferret will not attempt to become any of the following. A proposal to add functionality that crosses these boundaries requires a new ADR and a revision to this document.

| Non-Goal | Rationale |
|---|---|
| **Integrated Development Environment (IDE)** | Ferret has no editor interface. It integrates with editors through MCP. |
| **Source Control System** | Ferret does not manage commits, branches, or repository history. It reads them. |
| **Issue Tracker** | Ferret does not manage work items. It integrates with issue trackers through the plugin interface. |
| **Build System** | Ferret does not compile, test, or deploy software. It integrates with CI/CD through its CLI. |
| **AI Model** | Ferret does not perform model inference. It consumes model providers through the plugin interface. |
| **Cloud Platform or Hosted Service** | Ferret is a locally deployable platform. A hosted version is not part of this product's scope. |
| **General-Purpose Agent Platform** | Ferret provides an agent runtime scoped to engineering workflows only. General-purpose orchestration is out of scope. |
| **Documentation Generator** | Ferret consumes documentation as knowledge input. It does not generate static documentation sites. |
| **Code Formatter or Linter** | Ferret does not enforce code formatting. It integrates with formatters through CI hooks. |
| **Project Management Platform** | Ferret does not manage sprints, velocity, or team planning. |

## 10. Functional Requirements

Requirements are grouped by platform capability. Each requirement is assigned:
- **ID**: `FR-[CATEGORY]-[NNN]`
- **Priority**: P1 (Must), P2 (Should), P3 (Could)
- **Description**: What the system must do
- **Acceptance Criteria**: The observable condition that proves the requirement is met
- **Dependencies**: Other requirements that must be satisfied first

### 10.1 Workspace

| ID | Priority | Description | Acceptance Criteria | Dependencies |
|---|---|---|---|---|
| FR-WS-001 | P1 | The platform must initialise a workspace in any directory that contains a version-controlled repository | `Ferret init` completes without error; `.ai/workspace.json` is created; running `Ferret init` again on the same directory is a no-op | None |
| FR-WS-002 | P1 | The platform must validate the workspace configuration on startup and report any invalid or missing required fields with actionable error messages | `Ferret workspace validate` exits 0 on a valid workspace and exits non-zero with a structured error list on an invalid one | FR-WS-001 |

## 12. Product Modules

The following modules constitute the Ferret platform. Module descriptions define the responsibility of each module. Implementation is addressed in architecture documents.

| Module | Responsibility |
|---|---|
| **Workspace Engine** | Initialises and validates the workspace; manages the `.ai/` directory lifecycle; reports workspace health and status |
| **Knowledge Engine** | Provides the query interface over the knowledge index; manages the knowledge schema; assembles context for AI interactions |
| **Index Engine** | Builds and maintains the knowledge index; manages incremental updates; enforces atomicity of index writes; coordinates with Parser plugins |
| **Memory Engine** | Persists and retrieves session state; manages decision records; produces session summaries; links memories to repository artefacts |
| **Artifact Engine** | Manages the lifecycle of AI-generated artefacts; records provenance metadata; enforces the human-review requirement |
| **Specification Engine** | Manages specification lifecycle (Draft → Approved); validates specification completeness; links specifications to implementations |
| **Review Engine** | Generates AI-assisted review drafts; manages finding lifecycle; enforces human approval of AI findings; records review dispositions |
| **Plugin Host** | Loads, validates, and manages plugin lifecycle; enforces plugin permission model; isolates plugin failures |
| **CLI** | Provides the developer-facing command interface; routes commands to appropriate engines; manages output formatting and exit codes |
| **MCP Server** | Exposes platform capabilities as MCP tools and resources; manages MCP transport lifecycle; serves MCP client connections |
| **Telemetry** | Manages structured logging, distributed tracing, and metrics emission; coordinates export to configured backends |
| **Configuration** | Loads, merges, and validates platform configuration; resolves environment variable substitutions; provides configuration schema |

## 14. Future Scope

The following capabilities are not in scope for version 1.0 or 1.x, but are consistent with the long-term vision and may be addressed in future major versions.

**Multi-Repository Knowledge Federation.** A workspace that spans multiple repositories, with a federated knowledge index that allows queries to cross repository boundaries. This requires a defined cross-repository knowledge schema and a federation protocol.

**Hosted Read-Only Knowledge Mirror.** A read-only, hosted copy of a project's knowledge index that external contributors can query without cloning the full repository. This requires authentication, access controls, and a defined hosting model.

**Real-Time Collaborative Specification Authoring.** Multiple authors editing a specification simultaneously, with conflict resolution. This requires an operational transformation or CRDT-based approach to specification storage.

**Automated Specification Gap Detection.** Analysis of a codebase to detect implementation patterns that lack corresponding specifications, surfacing specification debt. This requires a semantic mapping between code structure and specification intent.

**Plugin Marketplace.** A curated registry of vetted, signed, and categorised plugins with automated compatibility verification. This requires a governance model for plugin submission and a verification infrastructure.

## 15. Out of Scope

The following capabilities are permanently out of scope. A proposal to add any of these requires a revision to this document and an ADR recording the decision.

| Capability | Rationale |
|---|---|
| Integrated Development Environment | Ferret integrates with IDEs through MCP. Building an IDE is outside the platform's purpose. |
| Source Control Operations | Ferret reads version control history. It does not manage commits, branches, merges, or remotes. |
| Issue Tracker | Work item management is not a platform function. The platform links to external issue trackers through the plugin interface. |
| Build and Test Execution | Executing compilers, test runners, or deployment pipelines is not a platform function. |
| AI Model Inference | The platform consumes AI models through the provider interface. Building or hosting models is not a platform function. |
| Cloud Platform or SaaS | The platform is locally deployable. Hosting infrastructure for others is not a platform function. |
| Code Formatting and Linting | Static analysis of code style is not a platform function. The platform integrates with formatters through CI. |
| Project Management | Sprint planning, velocity tracking, and resource management are not platform functions. |
| General-Purpose Document Management | The platform manages engineering artefacts only. General-purpose document storage is not a platform function. |

## 18. Assumptions

**A-001.** The target development environment has .NET 9 installed. The platform does not bundle a .NET runtime.

**A-002.** The repository being managed is version-controlled with Git. Other version control systems are not tested in version 1.0.

**A-003.** The user who initialises the workspace has write access to the repository's `.ai/` directory.

**A-004.** At least one model provider plugin is available and configured before AI-assisted features are used. The platform's non-AI features (indexing, specification lifecycle, review document creation) function without a model provider.

**A-005.** The knowledge index resides on a local filesystem with read/write access. Network-mounted filesystems are not a supported configuration in version 1.0.

**A-006.** Plugin packages are obtained from sources the user trusts. The platform validates plugin manifests but does not verify publisher identity in version 1.0.

**A-007.** The platform operates as a single-user tool in version 1.0. Multi-user concurrent write access to the same index is not a tested configuration.

## 19. Constraints

### C-001 — Vendor Neutrality
The platform must not require, prefer, or optimise for any specific AI model provider, cloud vendor, or commercial service. All vendor-specific integrations are delivered through the plugin interface.

### C-002 — Open Standards
Where a standard exists for a capability (MCP for model context, OpenTelemetry for observability, JSON Schema for configuration), the platform uses the standard rather than defining a proprietary format.

### C-003 — Cross-Platform
The platform must function identically on Linux, macOS, and Windows. No feature may be available on one platform and absent on another without an explicit documented exception and an ADR.

### C-004 — Plugin Architecture
No domain-specific capability may be implemented in the core platform. Every such capability must be implemented as a plugin. This is not a guideline; it is a structural constraint enforced through the architecture.

### C-005 — Repository Local Knowledge
The knowledge index must be stored within the repository. No knowledge about a repository may be stored only in an external service.

### C-006 — Specification First
The platform must enforce — not merely support — the requirement that specifications are approved before implementation begins. The enforcement is structural: the platform does not provide a mechanism to bypass it.

### C-007 — Human Review Mandatory
The platform must not provide any mechanism for committing AI-generated artefacts without human review. This constraint applies to all artefact types and all review mechanisms, including automated CI-based review.

Artifact engine. Provenance metadata recording. Human-review enforcement. Artifact lifecycle management. Traceability from artefact to interaction to knowledge state.

Plugin host. Plugin manifest schema. Permission enforcement. Plugin failure isolation. Plugin scaffold and validate CLI commands. Plugin SDK NuGet package. First-party model provider plugin.

MCP server — stdio and HTTP/SSE transports. Knowledge query tool. Context assembly tool. MCP client mode. MCP tool schema versioning.

Full CLI command surface for all platform operations. All output formats. Shell completion. Dry-run support. Exit code consistency. CLI documentation.

Specification completeness validation. Review engine. ADR engine. Performance benchmark suite. Integration tests. Release packaging. NuGet publication. Plugin registry. v1.0 announcement.

## 22. Release Strategy

### 22.1 Pre-Release Versioning

| Stage | Version Pattern | Audience |
|---|---|---|
| Sprint-by-sprint builds | `0.x.y-alpha` | Core contributors only |
| Feature-complete, hardening | `0.x.y-beta` | Early adopters, plugin developers |
| Release candidates | `1.0.0-rc.N` | Broad community testing |
| General availability | `1.0.0` | All users |

### 22.2 Release Criteria for v1.0

- All P1 requirements in Section 10 are implemented and verified.
- Unit test coverage for `Ferret.Core` and `Ferret.Runtime` is ≥ 85%.
- Zero open Critical or High security findings.
- All CLI commands documented in `docs/006-CLI/`.
- At least one working model provider plugin and two parser plugins published.
- At least one complete user journey (Journey 1) verified end-to-end.
- All public interfaces documented in `docs/007-SDK/`.

### 22.3 Compatibility Commitments

Once version 1.0 is released:

- The CLI command surface does not change in a backwards-incompatible way within any 1.x release.
- The plugin SDK interfaces do not change in a backwards-incompatible way within any 1.x release.
- The MCP tool schemas do not change in a backwards-incompatible way within any 1.x release.
- The knowledge index format does not change in a way that requires a full rebuild within any 1.x release.

Breaking changes require a major version increment, an ADR, and a migration guide.
