## Real task performed

Investigated a real dependency question (an IdentityModel version decision already flagged in the external repo's own files) using `ferret search` as the primary tool, per the "do real work, not synthetic testing" operating mode.

## Findings

1. **Bug — `ferret search` rejects all hyphenated queries.** `ferret search "nem-3795"` and `ferret search "test-hyphen"` both failed with `Invalid query: empty or whitespace` — a misleading message, since the input was neither. Root cause traced: `QueryTranslator.EscapeKeyword` treated `-` as safe/unquoted, but SQLite FTS5's query grammar treats a bare `-` as its NOT operator (`nem-3795` parsed as `nem AND NOT 3795`); the resulting provider failure's diagnostics were then silently dropped in `SearchService.SearchAsync`, so the CLI fell back to its generic empty-query message. Filed as [#15](https://github.com/indoulia/Ferret/issues/15), **fixed via TDD** (commit `366cc3d`): quote hyphenated keywords like any other special character. Full suite green.
2. **Bug — `packages/` (NuGet cache) not in the default indexing skip list.** Searching the external repo for a real dependency question returned 20 results, **all vendored package XML doc-comments**, drowning out the actual hand-authored analysis document, which never appeared. `node_modules`/`bin`/`obj` were already excluded; `packages` (the equivalent for classic-style .NET projects) was not. Filed as [#16](https://github.com/indoulia/Ferret/issues/16), **fixed via TDD** (commit `bedbc94`): added `packages` to `HardcodedSkipDirs`. Full suite green.
3. **Verified fix completeness for yesterday's #14** using `ferret search "AbsolutePath"` on this repo itself — confirmed both fixed call sites now show `Uri.UnescapeDataString(...)` in the indexed content, and no other production code path has the same unescaping gap (other `AbsolutePath` hits are unrelated HTTP-URI contexts). Real, useful validation loop: the tool being fixed was used to verify its own fix.
4. **Documentation gap (not fixed, flagged for review):** `docs/dogfooding/DOGFOOD-001.md` Phase 2 (lines 82, 84) instructs using `ferret ask`, which does not exist as a CLI command — confirmed via `ferret --help`. Closest real equivalent is `ferret context <query>`. Not corrected here: it's a governance document, out of scope for me to edit without authorization.

5. **Performance finding — `ferret watch` search-visibility latency far exceeds the ≤5s target (not fixed, no confident root cause).** First real exercise of `watch` this session: started it, saved a file with a distinctive marker, polled `ferret search` for it. The index DB file was touched only 0.64s after the save (fast), but the content was still not searchable after 27s of polling; it did eventually become searchable, but the exact crossover time wasn't captured (polling stopped at 27s; a later manual retry succeeded). `FileChangeDebouncer`'s configured window is only 500ms, so it can't explain the gap alone. Filed as [#17](https://github.com/indoulia/Ferret/issues/17) with the measurement caveats stated plainly — **not fixed**, since I don't have a confident root cause to act on (per the "don't guess a fix" rule). Process hygiene note: had two throwaway `ferret watch` background processes running mid-investigation; verified each one's exact PID via its command line and creation time before stopping it, after a blocked attempt to force-kill an unverified PID.
